# 節點服務契約草案

本文件整理以能力為基礎的聯邦協作（Capability-based Federation）的共用資料與行為，供後續實作討論。欄位與版本仍可調整，現有 SSH JSON 介面維持原有格式，實作進度見 [TODO](../TODO.md)。

## 身分、服務與能力

每個節點以可驗證的身分參與，節點內的每項服務使用獨立服務 ID。同一節點可提供多項服務。模型規模、可驗證能力及 Agent 角色分別宣告，各項服務按授權及資源條件接收請求。

| 服務類型 | 提供內容 |
| --- | --- |
| `build.runner` | 建構、測試及程式碼檢查任務 |
| `ai.inference` | 模型推論 API，可提供串流輸出 |
| `ai.agent` | 帶工作流程及授權工具的 Agent 執行 |
| `ai.orchestrator` | 任務拆解、委派與結果整合 |
| `mcp.provider` | 透過 MCP 提供工具、資源與其他已授權功能 |

服務描述至少包含以下資訊。個別服務再以版本化的擴充描述模型、工具鏈或工具清單。

| 欄位 | 語意 |
| --- | --- |
| `contract_version` | 共用契約版本。主要版本不相容時拒絕請求，必要能力須明確協商。 |
| `node_id`、`service_id` | 已驗證節點身分與節點內服務識別。顯示名稱可另外設定。 |
| `service_type`、`service_version` | 服務種類及其個別契約版本。 |
| `capabilities` | 能力宣告，包含宣告來源、驗證狀態及可取得的測試證據。 |
| `environment` | 平台、架構、工具鏈、模型修訂或執行環境等相容性條件。 |
| `resources` | 資源需求格式、配置上限、實測餘裕、保留額與可分配量。未知值明確表示。 |
| `access_policy` | 可呼叫的身分與操作範圍，敏感政策可由節點本地保存，對外公布政策識別。 |
| `status`、`observed_at`、`valid_until` | 最後回報的服務狀態、UTC 時間及有效期限。 |
| `transport` | 已授權的傳輸介面及介面版本，例如既有 SSH 適配器。 |

能力、資源及測試成績可分別過期。路由選擇時檢查其有效性，接收端在接單時重新確認資源與授權。第一版用明確的擴充欄位承載額外資料，必要擴充與版本須先協商。

## 第一版資料結構

[服務描述 Schema](../schemas/service-description.schema.json) 使用 JSON Schema Draft 2020-12，目前的共用契約版本為 `0.1-draft1`。這是可修改的草案版本，第一版接收端應精確核對支援的版本。個別服務版本與傳輸版本各自協商。

兩份範例分別為 [build.runner](../examples/services/build-runner.json) 和 [ai.inference](../examples/services/model-inference.json)。節點 ID、政策、模型與時間皆為示例，能力驗證狀態為 `unverified`。範例展示格式，接收端功能依後續實作驗收。

共用欄位採用 snake_case。核心欄位必填，無讀值的資源量使用 `null`。所有 byte 數為非負整數，時間使用結尾為 Z 的 UTC 日期時間。狀態為 `unknown` 的資源，其實測餘量與有效可派工量都為 `null`；`stale` 可保留歷史餘量，有效可派工量為 `null`。

未知的核心欄位會被結構驗證拒絕，額外資料放進以命名空間命名的 `extensions`。接收端可忽略選填擴充。若擴充列入 `required_extensions`，接收端須確認內容存在且理解其契約後才使用服務。服務類型採用可擴充的名稱，執行前由接收端確認對應的處理器及版本。

結構驗證器需啟用 date-time 格式檢查。例如 Python 的 jsonschema 套件需安裝日期格式檢查所需的額外依賴，並使用 `Draft202012Validator` 搭配 `FormatChecker`。驗證前應確認 checker 支援 `date-time`。[JSON Schema 物件欄位說明](https://json-schema.org/understanding-json-schema/reference/object) · [格式驗證說明](https://python-jsonschema.readthedocs.io/en/stable/validate/#validating-formats)

接收端另外執行以下語意檢查，並提供具體拒絕原因。

| 項目 | 判定 |
| --- | --- |
| 身分綁定 | `node_id` 與已認證的連線身分對應，`service_id` 屬於該節點。能力宣告者與來源一致。 |
| 唯一性 | 同一節點的服務 ID，以及描述內的能力 ID 與資源池 ID 均無衝突。 |
| 時效 | `valid_until` 晚於 `observed_at`，服務與必要資源仍有效。過期資料觸發重新查詢。 |
| 證據 | `verified` 至少附一筆證據。接收端再確認驗證者可信、證據可取得、時間有效，且對應同一環境或模型修訂。 |
| 資源 | 可用名額不超過最大並行數，保留額與配額一致，共用容量池依 scope 合併計算。未知的必要資源重新量測或拒絕。 |
| 擴充與服務版本 | 必要擴充存在且受支援，個別服務與傳輸版本有相容處理器。 |

上述跨欄位、時效與信任檢查待實作於接收端。個別服務的 environment 內容也需後續服務專屬的 Schema 驗證。

## 授權與跨節點委派

連線身分驗證完成後，接收端逐項判定服務呼叫、資料存取、工具使用與再委派權限。持有大型模型或協調角色的節點，其可執行操作以原提交者和接收端共同允許的範圍為準。

請求的授權描述涵蓋提交者、目標服務、資料／快照識別、允許的工具與操作、允許轉送的節點、有效期限及可用預算。憑證由傳輸適配器或授權機制處理，避免憑證出現在公開服務描述、任務日誌與診斷結果中。

服務描述中的 `access_policy` 指向接收端本地的政策 ID 與修訂，並列出該服務可接受的操作。預設判定為 deny。操作清單須和本地政策及原始授權一起判定。接收端依序完成以下步驟後才保留資源或執行操作。

1. 認證呼叫者，確認目標節點、服務與支援版本。
2. 載入有效政策並核對修訂。政策遺失、已撤銷或修訂失效時拒絕。
3. 核對操作、資料、工具、有效期限及剩餘預算，取呼叫者授權與本地政策允許範圍的交集。
4. 若有委派，查證父任務的授權鏈及允許的接收節點。未授予的再委派權限按禁止處理。
5. 在接單鎖內重新確認授權有效性與資源，配置本次執行並記錄決策。

拒絕原因至少區分不支援版本、不支援服務或必要擴充、身分不符、政策缺失或失效、授權過期、操作未獲允許與資源不足。授權憑證的封裝、簽署及跨傳輸驗證機制需在請求契約中繼續定義。

委派時取原始授權與各接收端政策的交集，並配置父子任務識別。限制委派深度、重試次數及累積時間或資源預算。每次再委派重新判定接收者及可轉送資料。撤銷授權後停止接受後續操作，依服務契約取消進行中的操作並回報清理結果。已交付的資料及已發生的外部副作用需保留可追查紀錄。

驗收包含可信節點中的未授權服務拒絕、私人快照轉送限制、超出工具權限、委派循環及授權撤銷。

## 服務與請求的生命週期

服務回報 `ready`、`busy`、`draining` 或 `unavailable`。停止接新請求但仍處理既有工作的服務使用 `draining`。狀態過期或連線失敗時，觀察端記錄最後有效狀態並顯示 `unknown` 與失聯時間，等待重新查詢。

| 階段 | 共同行為 |
| --- | --- |
| 提交 | 提供請求 ID、服務版本、輸入識別、需求與授權。 |
| 接受／拒絕 | 接收端驗證後配置資源。拒絕回報原因，接受回傳任務 ID、執行 ID 及適用的期限。 |
| 執行 | 回報狀態、診斷與進度。批次任務回傳日誌與產物，推論服務依其協定串流輸出。 |
| 完成 | 回報成功、失敗或逾時，以及可取得的結果與資源釋放狀態。 |
| 取消 | 接收取消請求後回報處理狀態，確認執行已停止及必要清理後再標記取消完成。 |

請求 ID 用於同一提交者的重複提交判定。同 ID 且內容相同時回傳既有接受或結果資訊，同 ID 但內容不同時拒絕。任務 ID 識別工作，執行 ID 識別一次嘗試。重試沿用任務 ID 並配置新的執行 ID。提交端依有效執行判定整體結果，保留晚到的舊結果供追查。

持續推論與 Agent 工作階段需另外定義工作階段 ID、租期與續期。連線中斷後是否繼續、串流能否重播、取消傳遞，以及外部副作用的去重，各由服務契約明確規定。SSH 傳輸中斷可回報執行結果未知，提交端先查證再決定重試。

## 現有 build.runner 的對應

| 現有介面 | 共用契約的對應與差距 |
| --- | --- |
| SSH 金鑰與強制命令 | 已有接收入口授權。節點／服務 ID、細分操作及委派授權待實作。 |
| `capabilities` | 已回報平台、映像及名額。服務描述版本與能力驗證資訊待實作。 |
| `diagnostics` | 已有資源、接單原因與執行中任務。狀態有效期限與服務生命週期待實作。 |
| `submit` | 已同步接受或拒絕並回傳結果。請求去重、獨立執行 ID 及取消協定待實作。 |
| 結果與產物 | 已保存執行節點結果並回傳提交端。輸入快照識別與重試結果判定待實作。 |

共用契約先透過現有 build 任務驗收，再擴展至模型與 Agent。遷移時保留既有 CLI 入口，新增版本協商與適配，並驗收舊任務描述及既有結果的讀取。

## 接續設計與驗收順序

1. 確認必要欄位、身分對應、授權描述與版本協商，再定義可驗證的資料結構。
2. 以 build.runner 實作請求去重、執行 ID、取消及舊資料相容。
3. 定義 ai.inference 的請求、串流、取消、並行與模型能力驗證。
4. 定義 Agent 父子任務、預算、授權繼承及雙向委派，再接入協調流程。

上述順序用於能力契約工作。現有 worker 的工作區硬配額與離線容錯仍保留各自的實作與驗收項目。
